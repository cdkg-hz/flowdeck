# 白鲸智存更新日志维护约定

## 发布文件

一次产品发布对应：

1. 在 `changelog.html` 的版本列表顶部新增一个版本区块，包含版本号、日期和分类概要。
2. 新建一个同名版本详情 HTML，例如 `2.1.1-114.html`。
3. 保留历史详情页不变；只有明确勘误时才修改旧版本。

## 版本与日期

- 发布标识采用 `{versionName}-{versionCode}`，例如 `2.1.1-114`；历史版本没有 `versionCode` 时只写 `versionName`。
- 文件名、页面标题和列表中的 `Version:` 文案必须完全一致。
- 日期采用实际发布日期或对应版本文档日期，不采用生成 HTML 的日期。
- 版本列表按发布时间从新到旧排列。

## 主页概要

- 每个版本在 `changelog.html` 中直接展示内容概要，不能只显示版本号和日期。
- 概要沿用详情页中实际存在的分类，先列核心更新，再补充其他重要且用户可感知的变化。
- 概要用于让读者不进入详情页也能了解本版主要内容，但不展开操作步骤或技术实现；版本号和“查看完整版本说明”均链接到独立详情页。
- 首发基线版本使用“首发版本功能”，不使用“新增功能”。

## 详情页分类

- 首发版本使用“首发版本功能”，不使用增量发布分类。
- 首发后的版本至少包含以下分类；如有必要，可增加“改进”“兼容性与安装”等分类：

1. 新功能
2. 问题修正
3. 注意事项

条目优先按“微信小程序、柜端屏幕、管理后台、平台服务”等用户可识别的端归组。每条只描述一项用户、运营或实施人员能够感知的变化。

## 内容来源与边界

1. 先以该版本产品手册中标明“已支持”的能力为依据。
2. 再用技术说明书和实际代码核对能力是否已经存在。
3. 未实现、仅有入口或仍有限制的能力，不写成新增功能；必要时放入“已知问题”。
4. 发布说明不包含代码、接口地址、源码文件名、源码路径、内部审计过程或长篇操作步骤。
5. 新版本只写相对上一版的增量，不重复罗列已经发布的基线能力。

## 发布前检查

- 从本地直接打开 `changelog.html`，确认所有版本链接可进入对应详情页。
- 确认每个详情页的“返回更新日志”链接可用。
- 检查桌面与手机宽度下无横向滚动、文字不溢出。
- 核对列表版本号、详情页标题、文件名与发布日期一致。
- 确认空分类没有显示，历史详情页没有被无意修改。
