# 任务：生成产品版本更新日志

基于旧手册、新手册、新说明书摘要和 `.flowdeck-changes.diff`，写一份给对外 HTML 用的增量稿：

`docs/updata_log/更新日志_{{DOC_DATE}}.md`

回答：这一版用户能感知到什么变化，以及还有哪些未闭环。不要做架构审计，不要写十二章全书。

---

## 输入

- 旧版《产品功能介绍与使用手册》
- 新版《产品功能介绍与使用手册》（P1a）
- 新版《现状技术实现与架构说明书》摘要（P1b）
- `.flowdeck-changes.diff`

路径来自 `payload.release.baseline_docs` 与 P1 新文件。某侧缺失则该侧结论标「文档无法确认」。

`commits.txt` / git log 不能当正文来源；diff 可以作为辅助证据。不要重写手册或说明书，不要改 HTML。

---

## 硬规则

1. 先读旧手册和新手册，再判断变化。禁止看到新版本存在某功能就定为「本版本新增」。
2. 禁止把「新版本文档新增描述」当成「产品功能真正新增」。没有旧手册或 diff 旁证时写「文档无法确认」。
3. 说明书摘要里标明未实现、仅入口、部分实现、有限制的，不得写成新增或已完成修复。
4. 未变化的功能不要为凑篇幅罗列。
5. 不要猜测。证据不足写「文档无法确认」。

变化类型（内部判断，写入对应小节即可）：

- **新增**：旧版明确没有，新版明确有，且是真实产品能力
- **增强**：旧版已有，新版扩大或完善
- **变更 / 移除**：规则、入口或行为变了，或旧版有、新版可证明没有
- **修复**：用户可感知的问题被修好
- **无法确认**：材料不够，不要写成确定事实

---

## 产出结构

```markdown
# 产品更新日志

**版本对比：** 旧版本日期 → {{DOC_DATE}}

## 一、用户可感知变化

按端归组（有则写，没有则整节省略）：微信小程序、柜端屏幕、管理后台、平台服务。

每条一行：变化类型 + 一句话说明。不要操作步骤，不要代码、接口、源码路径。

## 二、注意事项与未闭环

说明书摘要和手册边界里仍未闭环、仅入口、有限制的项。无则整节省略。

## 三、文档无法确认

有争议或证据不足的项。无则整节省略。
```

不要写：产品形态专章、八条业务流程专章、十一维技术架构、产品↔技术对照大表、旧问题逐条复核长表、另写一遍 TOP 10。
