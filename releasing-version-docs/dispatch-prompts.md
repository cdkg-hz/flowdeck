# 写作要点

本文件给同一 Flowdeck Agent 用，不是子任务派发词。规范全文在 payload.skills 的同名 `.md` 里，不要去读 `.cursor/skills/`。

工作区根目录：当前可写工作目录。输出目录：`docs/updata_log/`。日期用 `payload.release.docs_date`。发布标识用 P0 规则。

---

## 1. 产品手册

先读完「角色设定和任务目标」中「文档一：《产品功能介绍与使用手册》」。不要把文档二写进这一份。

有旧版手册时复制为新日期文件，只修订 `.flowdeck-changes.diff` 能证明的用户可感知变化；未改章节整段沿用。不要普查四端代码，不要从零重写。禁止用 README、需求文档、注释或项目名脑补未实现功能。入口存在但实现不完整、仅 Mock/占位，用非技术语言标出。不确定就写“不确定”。

读者：客户、运营、实施、客服。只写用户能看到、能操作、能理解的功能和流程。

禁止出现：代码目录、文件路径、函数名、组件名、接口路径、数据库表、技术栈细节。

写入：`docs/updata_log/产品功能介绍与使用手册_{{DOC_DATE}}.md`

---

## 2. 技术说明书

先读完「角色设定和任务目标」中「文档二：《现状技术实现与架构说明书》」。不要把文档一写进这一份。

只写约一页摘要：本版实现变化、未闭环、一句范围。只根据旧说明书与 diff 判断，不要打开 diff 未涉及的文件，不要目录树、接口、源码路径或流程链路。禁止把需求文档、README、注释里的功能当成已实现。

实现状态仅用于 diff 能判断的模块：已实现 / 部分实现 / 仅入口/占位 / 疑似废弃/遗留 / 未发现实现。

读者：给更新日志和对外 HTML 核对「未实现不要写成新功能」。不要写成研发接手档案。

写入：`docs/updata_log/现状技术实现与架构说明书_{{DOC_DATE}}.md`

---

## 3. 更新日志

先读完「生成新版本的更新日志」并按其硬规则和产出结构写。不要重写手册或说明书，不要改 HTML。

输入：

- 旧版产品手册、新版产品手册
- 新版技术说明书摘要
- `.flowdeck-changes.diff`

路径来自 `payload.release.baseline_docs` 与 P1 新文件。版本对比：旧日期 → `{{DOC_DATE}}`。发布标识仅供文内引用。不得用 git log / commits.txt 当正文来源。

硬规则：

- 禁止：看到新版本存在某功能就认定为“本版本新增”
- 禁止：把“新版本文档新增描述”当成“产品功能真正新增”
- 说明书摘要标明未实现或仅入口的，不写成新功能；证据不足写“文档无法确认”
- 不要写产品形态、流程、技术架构专章或对照大表

写入：`docs/updata_log/更新日志_{{DOC_DATE}}.md`

---

## 4. 对外 HTML

先读完「changelog-convention」。不要改 Markdown 手册、技术说明书或更新日志。不要改历史版本详情页。

版式：复制 `docs/updata_log/changelog.html` 与当前列表最上方那一版详情页的结构与样式，不要另起一套 CSS。

- 发布标识：`{{VERSION_ID}}`
- 页面日期：`{{DOC_DATE}}`
- 文件名、详情页标题、changelog 列表里的 `Version:` 文案必须完全一致

内容优先级：新版产品手册已支持能力 → 技术说明书/必要代码核对 → 更新日志增量。只写相对上一版的增量。未实现、仅入口、仍有限制的不写成「新功能」。

禁止：代码、接口地址、源码文件名、源码路径、内部审计过程、长篇操作步骤。

条目按用户可识别的端归组。分类：新功能、问题修正、注意事项；空分类整段不出现。本增量版本不要用「首发版本功能」。

产出：

1. 新建 `docs/updata_log/{{VERSION_ID}}.html`；「返回更新日志」指向 `changelog.html`
2. 更新 `changelog.html`：列表顶部插入本版本、版本计数 +1、「最新」徽章移到本版本；不得修改历史详情页文件
